# 大模型协作开发记录 (AI Collaboration Record)

在本项目的开发过程中，团队三人（分别负责FPGA底层逻辑、串口通信控制、Python上位机开发）深度使用了 DeepSeek 等大模型作为辅助工具。我们始终遵循“**AI 生成语法骨架，人工审查物理边界**”的原则，没有盲目复制 AI 输出，而是将其定位为“高级代码生成器”与“排错助手”。

以下为团队在不同模块的典型协作与纠错记录：

## 1. 典型提示词与模型初步回答 (Prompt & Response)

团队在各自模块开发中，利用大模型快速跨越了底层语法和样板代码的编写阶段。以下为典型场景：

### 1.1 底层逻辑与物理时序
*   **Prompt**：我的 UART 接收模块用 `Rx_Done` 脉冲触发 32 位频率字更新，但切频时仿真波形总有毛刺，帮我看看组合逻辑。
*   **AI 回答**：建议采用一个多路选择器（MUX），在 `Rx_Done` 为高电平时更新频率字。还给出了一段组合逻辑代码：`assign dds_ftw = Rx_Done ? ftw : ftw_reg;`，并建议在时钟上升沿将 `dds_ftw` 锁存到寄存器中，这样可以“保证在脉冲到来时无缝切换频率”。

### 1.2 串口通信与控制逻辑
*   **Prompt**：我写了一个 UART 接收模块，用下降沿检测来触发波特率分频计数器使能，但仿真时偶尔会把噪声当起始位，接收数据错乱，帮我看看逻辑。
*   **AI 回答**：建议直接对 `uart_rx` 信号做边沿检测，检测到下降沿就拉高 `en_baud_cnt` 开始采样。
*   **Prompt**：我要解析上位机下发的波形和频率指令，帮我设计一个解析模块。
*   **AI 回答**：给出了一套复杂的二进制帧协议，包含帧头 `0xA5`、帧尾 `0x5A`、命令字及校验字节的状态机。

### 1.3 上位机软件
*  **背景**：由于分工原因，团队在编写上位机时还无法使用FPGA板子进行真实联调，串口通信模块处于“无对端”状态。
*  **Prompt**：我们向 AI 描述了团队约定的串口协议。
*  **AI 回答**：AI 据此生成了独立的上位机联调工具 `fpga_simulator.py`，完整模拟 FPGA 端的串口行为（收到合法指令自动应答 `STA:OK`，收到非法格式/越界参数分别应答 `STA:ERR:01/02`）。
*   **Prompt**：Python 的 tkinter 界面在接收 921600 波特率的串口数据时直接卡死，怎么解决？
*   **AI 回答**：建议使用 `threading.Thread` 守护线程读取串口，并将数据放入 `queue.Queue`，主线程通过 `root.after()` 定时轮询更新 UI，避免阻塞主循环。
*  **Prompt**：界面存在按钮文字被截断、日志区被挤压只剩空白、扫频按钮被面板裁剪消失等问题。
*  **AI 回答**：逐轮分析根因并修改代码，期间排除了一个典型的顺序 Bug：滚动条创建时引用了尚未创建的日志控件导致程序启动崩溃（`AttributeError`），通过调整对象创建顺序解决。



## 2. 人工纠错与工程验证 (Self-Correction)

AI 生成的代码在语法上往往完美无缺，但在实际物理硬件、时序约束和容错处理上却隐藏着诸多漏洞。团队结合仿真与板级实测，进行了以下核心纠错：

### 2.1 跨时钟域与逻辑漏洞修补
*   **UART 亚稳态与裸边沿触发**：AI 给的直接下降沿检测方案，外部异步输入没有任何同步，极易采到亚稳态且采样点不在位中心。团队改为对 `uart_rx` 做**三级寄存器打拍同步**（`dff0_uart_rx → dff1_uart_rx → r_uart_rx`），用 `dff1==0 && r_uart_rx==1` 判断稳定后的下降沿；同时采样点取在 `MCNT_BAUD/2` 中点采样。
*   **频率字组合逻辑毛刺**：AI 建议组合逻辑直连 `ftw`。仿真发现同一拍数值还在跳变。团队在 `cmd_parser` 中打一拍，确保 `ftw` 与 `ftw_valid` 严格对齐，送入 DDS 进行非阻塞赋值锁存，消除毛刺。

### 2.2 拒绝过度设计，协议精简与容错
*   **Prompt**：请AI设计一个解析模块，AI给出了一套较复杂的二进制帧协议，包含帧头 `0xA5`、帧尾 `0x5A`、命令字、校验字节，还有一长串的协议状态机。
*   **工程判断与决策**：队员评估后认为这套帧协议对本项目过重——增加校验字节会拉高板级联调时的排错成本，也增加仿真工作量，参考了上位机同学的串口工具习惯之后改成更轻量的 **ASCII 明文命令**：`W0`~`W3` 设置波形、`F+频率字` 设置频率，以回车换行 `\r\n` 作为一帧结束标志。同时在 FSM 中为每条命令加了**非法字符兜底分支**——收到命令外的字符立即回 `S_IDLE`，杜绝"卡死在某个状态"的隐患。
*   **最终解决方案**：以 `cmd_parser` 为载体的三段式状态机最终采用 `S_IDLE / S_WAVE / S_FREQ` 三个状态，波形编号解析为 `Rx_Data - '0'`，频率按 `value*10 + (Rx_Data-'0')` 逐位累加，遇到 `\n` 才锁存 `wave_sel / ftw` 并拉高 `wave_valid / ftw_valid`。最终把"精简协议 + 容错状态机"的思路也写进了团队约定的接口文档。

### 2.3 硬件时序与工具链
*   **物理时序违例的抢救**：AI 无法感知底层布线的物理延迟。综合后系统出现 WNS 为负的违例，团队通过 Timing Summary 分析，定位到是 ILA 调试探针的长线拖垮了时序。在 XDC 中加入 `set_false_path` 忽略 ILA 路径，并在最终发版时移除 ILA，成功将 100MHz 时序收敛至 +0.226ns。
*   **Vivado 幽灵缓存排查**：在更新 COE 文件重新生成 ROM IP 后，仿真波形变成三角波。AI 提示可能是增量编译缓存残留。最终团队手动清空了工程目录下的 `.sim` 和 `.cache` 文件夹，并强制重新生成 IP 输出产物，波形恢复正常。


### 2.4 软硬件联合仲裁与并行验证
*   **双模式仲裁**：队友在顶层 `control_top` 里既接了串口指令解析结果，又接了 4 个按键，两个来源同时更新 `wave_sel` 和 `ftw`，怎么写仲裁逻辑最稳？AI 建议按键和串口“后到者优先”。
*   **工程判断与优化**：队友认为"后到者优先"在板级调试时不可控——按键误触会意外覆盖上位机下发的参数，导致调试现场很难复现。结合本项目"上位机为主、按键为本地应急"的定位，我定为 **串口指令严格优先于按键**：`if(serial_wave_valid) ... else if(key_wave_valid) ...`，确保任何时刻上位机参数不被按键干扰。另外把四个按键的**消抖脉冲**（`key_debounce` 输出的 20ms 稳定判定 + 边沿脉冲）统一接进 `key_control`，频率增减用固定步进 `FTW_STEP` 并加了上下限饱和，防止频率字溢出。
*   **最终解决方案**：顶层用"串口优先"的寄存器锁存方案输出 `wave_sel / ftw`，`ftw_valid` 取两路有效信号的或。板级联调时，按键模式与串口模式切换稳定、无毛刺，参数互不干扰。

## 3. 协作心得

AI 是团队开发过程中的“超级加速器”，它帮我们省去了大量查 API、写繁琐语法的时间。但我们也深刻认识到：**在 FPGA 领域，AI 缺乏对“物理延迟”和“时序约束”的感知**。它可能写出逻辑正确但跑不到 100MHz 的代码，也可能忽略跨时钟域的亚稳态风险。

最终的时序收敛、异常保护和系统架构，依然依赖于工程师扎实的硬件功底与严谨的工程验证。这次协作经历让我们学会了如何“驾驭”AI，让它成为我们探索物理世界的得力工具。
